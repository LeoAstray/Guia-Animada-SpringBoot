Proyecto y configuración 6 preguntasParte 1 · Data JPA

¿Qué dependencias marco al crear el proyecto en Spring Initializr?

Cinco: Spring Data JPA, MySQL Driver, Spring Boot DevTools, Spring Web y Validation.

  • Spring Data JPA trae JPA (relacionar clases con tablas), Hibernate (quien hace el trabajo) y los repositorios.
  • MySQL Driver es el «traductor» que permite a Java hablar con MySQL.
  • DevTools reinicia la aplicación sola cuando guardas cambios.
  • Spring Web y Validation no se usan hasta la API REST (Parte 2), pero si las marcas desde el principio no tendrás que tocar el pom.xml después. Spring Web es lo que permite recibir peticiones HTTP; Validation, usar @Valid y @NotBlank.

Si se te olvidó alguna, se puede añadir después en el bloque <dependencies> del pom.xml.

Paso 1 · Crear el proyecto en Spring Initializr

¿Qué hace spring.jpa.hibernate.ddl-auto y qué valor pongo?

Le dice a Hibernate qué hacer con las tablas al arrancar, a partir de tus entidades:

ValorQué haceCuándo usarlo
updateCrea las tablas que faltan y añade columnas nuevas. Conserva los datos.Mientras desarrollas y quieres que los datos sigan ahí al reiniciar.
create-dropCrea las tablas al arrancar y las borra al cerrar.Con un data.sql: cada arranque empieza limpio con los mismos datos.
createBorra y crea las tablas al arrancar (no al cerrar).Poco habitual en los ejercicios.
noneNo toca las tablas.Cuando la base ya está hecha y no quieres que Hibernate la cambie.
Pasar a update no recupera tablas que un cierre anterior con create-drop ya ha borrado. Usa siempre una base de práctica para las opciones que recrean tablas.

Paso 14 · Cargar los datos iniciales

¿Cómo hago que se ejecute el data.sql al arrancar?

El archivo va en src/main/resources/data.sql y necesita estas tres líneas en application.properties:

spring.jpa.hibernate.ddl-auto=create-drop
spring.sql.init.mode=always
spring.jpa.defer-datasource-initialization=true
  • create-drop crea las tablas desde las entidades al arrancar (y las borra al cerrar), así el data.sql no choca con datos de la vez anterior.
  • spring.sql.init.mode=always activa el data.sql también con MySQL (por defecto solo lo hace con bases en memoria).
  • defer-datasource-initialization=true espera a que Hibernate cree las tablas antes de lanzar los INSERT. Sin ella, los INSERT fallarían porque las tablas aún no existen.

Paso 14 · Cargar los datos iniciales

¿Por qué falla un INSERT del data.sql? ¿Importa el orden?

Sí, el orden importa: primero la fila a la que se apunta y después la que apunta. No puedes insertar un médico con id_hospital = 1 si el hospital 1 todavía no existe: MySQL lo rechaza por la clave foránea.

En el hospital, el orden correcto es: hospitales e historiales → médicos y pacientes → consultas. Si aun así falla, mira en la terminal la causa concreta: tabla inexistente, columna mal escrita, dato obligatorio que falta, clave repetida o una clave foránea que apunta a una fila que no existe.

Los nombres del data.sql son los de MySQL (id_hospital, fecha_nacimiento), no los de Java (hospital, fechaNacimiento). Y los enums se escriben con el texto exacto de la constante: 'CARDIOLOGIA', no 'cardiología'.

Paso 16 · Corregir errores y terminar el proyecto

¿Qué es CommandLineRunner y para qué sirve el método run?

CommandLineRunner es una interfaz de Spring. Si tu clase principal la implementa, tiene que escribir un método run, y Spring lo ejecuta solo, al terminar de arrancar: cuando ya están listos la conexión con la base y los repositorios.

Por eso es el sitio para hacer pruebas en la Parte 1: dentro de run puedes crear objetos, guardarlos con save, buscarlos y mostrarlos por consola. No hay que llamarlo desde main: lo llama Spring.

@SpringBootApplication
public class ExamenApplication implements CommandLineRunner {

    @Autowired
    private IJugadorRepository jugadorRepository;

    public static void main(String[] args) {
        SpringApplication.run(ExamenApplication.class, args);
    }

    @Override
    public void run(String... args) {
        // aquí van las pruebas
    }
}

Paso 8 · Ejecutar la primera prueba

La aplicación no conecta con MySQL. ¿Qué reviso?

Revisa, en este orden:

  1. Que MySQL está arrancado (en XAMPP, el botón Start de MySQL).
  2. El puerto de spring.datasource.url. En la guía es 3308; muchas instalaciones usan 3306. En phpMyAdmin, SELECT @@port; te dice cuál es.
  3. El nombre de la base, el usuario y la contraseña.

El mensaje de error da la pista: Access denied suele ser usuario o contraseña; Communications link failure significa que no se llega al servidor (está parado o el puerto es otro).

Paso 16 · Corregir errores y terminar el proyecto

Entidades 6 preguntasParte 1 · Data JPA

¿Qué es una entidad y qué hace cada anotación?

Una entidad es una clase Java que JPA sabe guardar en una tabla: cada objeto es una fila y cada campo, una columna.

AnotaciónQué hace
@EntityMarca la clase como entidad.
@Table(name = "medicos")Nombre de la tabla en MySQL.
@IdEl campo que es la clave primaria.
@GeneratedValue(strategy = GenerationType.IDENTITY)MySQL genera el id solo al insertar (autoincremento).
@Column(name = "id_medico", nullable = false, length = 80, unique = true)Nombre de la columna, si admite vacíos, longitud máxima y si se puede repetir.
@Enumerated(EnumType.STRING)Guarda un enum como texto.

Los imports son de jakarta.persistence. Si VS Code te ofrece javax.persistence, es el nombre antiguo: no lo aceptes.

Paso 6 · Crear la entidad Jugador

¿Por qué hace falta el constructor vacío si no lo uso?

Porque lo usa JPA. Cuando lee una fila de la base, primero crea un objeto vacío con new Medico() y después le rellena los campos con los datos de la fila. Sin ese constructor, JPA no puede leer tus entidades y la aplicación falla al arrancar.

Tú, para crear objetos, usa el constructor con parámetros. El vacío se queda para JPA.

Paso 11 · Añadir una relación uno a uno

¿Por qué no pongo el id en el constructor?

Porque el id lo pone MySQL al insertar la fila (GenerationType.IDENTITY). Un objeto recién creado con new tiene id = null; después de save, ya tiene el número que le ha dado la base.

Si generas el constructor con VS Code (Source Action → Generate Constructors), no marques id, ni tampoco las listas de relaciones (medicos, consultas): las listas nacen vacías y se llenan con los métodos add….

Paso 6 · Crear la entidad Jugador

¿Qué hace @Enumerated(EnumType.STRING)?

Guarda el enum en la base como texto: en la columna aparece CARDIOLOGIA. Sin esa anotación, JPA guardaría su posición en la lista (0, 1, 2…), y si un día cambias el orden de los valores del enum, todos los datos guardados pasarían a significar otra cosa.

En el data.sql y en el JSON de Postman hay que escribir exactamente el nombre de la constante: "PEDIATRIA", no "pediatría". Un valor que no existe da error (en la API, un 400).

Paso 13 · Representar una relación muchos a muchos

¿Por qué se usa BigDecimal para el dinero y no double?

Porque double no guarda los decimales de forma exacta: 0.1 + 0.2 da 0.30000000000000004. Con dinero eso es un error. BigDecimal guarda el número exacto.

Se crea desde un texto: new BigDecimal("4200.00"). En la columna se indica el tamaño con precision (cifras en total) y scale (cuántas son decimales): @Column(precision = 10, scale = 2) admite hasta 99.999.999,99.

Paso 12 · Crear una relación uno a muchos

¿Qué diferencia hay entre optional = false, nullable = false y unique = true?
  • optional = false (en @OneToOne o @ManyToOne) es una regla del modelo Java: la relación es obligatoria. JPA no deja guardar el objeto sin ella.
  • nullable = false (en @Column o @JoinColumn) es una regla de la base de datos: la columna no admite NULL.
  • unique = true también es de la base de datos: no puede haber dos filas con el mismo valor en esa columna.

En un uno a uno obligatorio, como paciente e historial, se ponen los tres: optional = false en la relación, y nullable = false, unique = true en su @JoinColumn. Sin unique, dos pacientes podrían compartir el mismo historial y la relación sería en realidad de uno a muchos.

Paso 11 · Añadir una relación uno a uno

Relaciones 12 preguntasParte 1 · Data JPA

¿Quién es el propietario de la relación, y por qué uno sí y el otro no?

En la base de datos una relación es una sola columna (por ejemplo, medicos.id_hospital). En Java, en cambio, la escribes dos veces: la lista medicos de Hospital y el campo hospital de Medico. Si los dos lados mandaran sobre la columna, JPA no sabría qué hacer cuando no coinciden. Por eso uno manda y el otro no.

  • El propietario es el que lleva @JoinColumn. Al guardar, JPA mira su campo para rellenar la columna. En el hospital es Medico.
  • El lado inverso es el que lleva mappedBy. No tiene columna: JPA lo usa para leer (rellenar la lista), pero no lo mira al guardar.

El propietario tiene que ser el lado cuya tabla guarda la columna, y en un uno a muchos la columna solo cabe en la tabla del lado «muchos». Por eso en un uno a muchos el propietario es siempre el lado del @ManyToOne.

Consecuencia práctica: si solo añades el médico a la lista del hospital y no haces medico.setHospital(hospital), la columna queda vacía, porque JPA solo mira al propietario. Por eso addMedico rellena los dos lados.

Paso 12 · ¿Quién es el propietario?

¿Por qué el @ManyToOne va en Medico y no en Hospital?

Porque una columna de una fila solo puede guardar un valor. Cada médico trabaja en un solo hospital, así que en su fila cabe id_hospital = 1. Al revés no se puede: un hospital tiene muchos médicos, y no hay forma de meter «2, 5 y 7» en una sola columna de la fila del hospital.

hospitales (id_hospital PK, nombre, ciudad)
medicos    (id_medico PK, nombre, salario, especialidad, activo, id_hospital FK)   <- aquí

El nombre se lee desde la clase donde está escrito: en Medico, «muchos médicos → un hospital», @ManyToOne; en Hospital, «un hospital → muchos médicos», @OneToMany(mappedBy = "hospital").

Paso 12 · ¿Por qué el @ManyToOne va ahí?

¿Qué hace fetch = FetchType.LAZY?

Decide cuándo se carga el objeto relacionado. Con LAZY (perezoso), al leer un médico JPA no trae su hospital: deja un «sustituto» (un proxy) que sabe su id, y solo lanza la consulta del hospital si de verdad lo usas, por ejemplo con medico.getHospital().getNombre().

Con EAGER (ansioso) trae el hospital siempre, lo uses o no. Si no escribes nada, @ManyToOne y @OneToOne son EAGER; @OneToMany y @ManyToMany son LAZY. Por eso se escribe LAZY a mano en el @ManyToOne: si listas 100 médicos, no quieres 100 consultas extra.

El sustituto solo se puede usar mientras la conexión con la base sigue abierta. Si lo usas después, salta LazyInitializationException (ver «Errores frecuentes»).

Paso 12 · ¿Qué hace fetch = LAZY?

¿El @ManyToOne lleva siempre @JoinColumn?

No es obligatorio, pero conviene ponerlo siempre. Sin él, JPA inventa el nombre de la columna juntando el nombre del campo y el de la clave a la que apunta: para hospital sería hospital_id_hospital. Funcionaría, pero no coincide con el nombre que pide el enunciado ni con el del data.sql, y los INSERT fallarían.

Con @JoinColumn(name = "id_hospital", nullable = false) eliges el nombre y haces la columna obligatoria. Lo que nunca lleva @JoinColumn es el lado inverso (el del mappedBy): ese lado no tiene columna.

Paso 12 · ¿Lleva siempre @JoinColumn?

¿Qué es mappedBy y qué nombre se escribe dentro?

mappedBy marca el lado inverso de una relación bidireccional. Significa: «esta relación ya está descrita en un campo de la otra clase; no crees otra columna».

Dentro va el nombre del campo Java del otro lado, no el de la columna SQL. En Hospital se escribe @OneToMany(mappedBy = "hospital") porque en Medico el campo se llama hospital. Escribir "id_hospital" sería un error: ese es el nombre de MySQL.

Paso 12 · Crear una relación uno a muchos

¿Qué es orphanRemoval y qué hace?

orphanRemoval = true significa: el hijo que se queda sin padre se borra. Si quitas una consulta de la lista del paciente (paciente.getConsultas().remove(consulta)), esa consulta se queda «huérfana» y JPA borra su fila al guardar los cambios. Sin orphanRemoval, quitarla de la lista no borraría nada en la base.

Se usa cuando el hijo no tiene sentido sin su padre: una consulta sin paciente, un estadio sin equipo.

Paso 12 · cascade y orphanRemoval

¿Qué diferencia hay entre cascade y orphanRemoval?

cascade = CascadeType.ALL: lo que le hagas al padre, házselo también a sus hijos. Si guardas el paciente, se guardan sus consultas nuevas; si lo borras, se borran.

orphanRemoval = true: si un hijo sale de la lista, se borra.

Lo que hacesSolo cascade = ALLSolo orphanRemoval = true
Guardar un padre nuevo con hijos nuevosSe guardan también los hijosLos hijos hay que guardarlos aparte
Borrar el padreSe borran sus hijosSe borran sus hijos
Quitar un hijo de la listaNo se borra nadaSe borra ese hijo

En resumen: cascade mira lo que le pasa al padre; orphanRemoval mira si el hijo sale de la lista. Se ponen juntos cuando el hijo no existe sin el padre.

cascade: si tiras la caja de juguetes, los juguetes van dentro. orphanRemoval: si sacas un juguete de la caja, ese juguete se tira.

Paso 12 · cascade y orphanRemoval

¿Cuándo no hay que poner cascade?

Cuando el hijo vive por su cuenta. Borrar un hospital no debe borrar a sus médicos; borrar un médico no debe llevarse el historial de consultas de sus pacientes; borrar un jugador no debe borrar los equipos que comparte con otros. Por eso Hospital y Medico llevan su lista con mappedBy y sin cascade.

En esos casos, si alguien intenta borrar un padre que tiene hijos, lo correcto es comprobarlo antes y responder 409 Conflict, no borrar en cadena (ver «¿Por qué 409 y no 500?»).

Paso 13 · Representar una relación muchos a muchos

¿Por qué el constructor de Consulta lleva el médico y el paciente?

Porque una consulta no existe sin sus dos extremos: es «este médico atiende a este paciente, en esta fecha, por este coste». Sus dos @ManyToOne son obligatorios, así que las columnas id_medico e id_paciente no pueden quedar vacías.

Si el constructor no los pidiera, podrías crear una consulta incompleta y el error solo saldría al guardar, como un fallo de la base. Pidiéndolos, el compilador no te deja olvidarlos: el error sale en rojo en el editor, antes de ejecutar.

public Consulta(Medico medico, Paciente paciente, LocalDateTime fecha, BigDecimal coste,
        TipoConsulta tipo, boolean seguimiento) { ... }

Después, paciente.addConsulta(consulta) la añade también a la lista del paciente para que los dos lados queden sincronizados. En la guía pasa lo mismo con Fichaje (jugador y equipo).

Paso 13 · ¿Por qué el constructor lleva los dos lados?

¿Cuándo uso @ManyToMany y cuándo una entidad intermedia como Consulta?

Depende de si la relación tiene datos propios:

  • Solo hay que unir (qué autores tiene un libro): @ManyToMany. JPA crea una tabla intermedia con dos ids y nada más.
  • La unión tiene datos (fecha, coste, tipo, precio, temporada…): una entidad intermedia (Consulta, Fichaje, Matricula). La tabla intermedia pasa a ser una entidad con sus columnas, y la relación se convierte en dos @ManyToOne.

Un @ManyToMany directo no puede guardar nada más que los dos ids, por eso en cuanto el enunciado pide un dato de la relación hay que crear la entidad.

Paso 13 · Representar una relación muchos a muchos

¿Para qué sirven los métodos como addMedico o addConsulta?

Para rellenar los dos lados de una relación bidireccional de una vez. Añaden el hijo a la lista del padre y, además, le dicen al hijo quién es su padre:

public void addMedico(Medico medico) {
    medicos.add(medico);         // lado inverso: la lista, en memoria
    medico.setHospital(this);    // lado propietario: el que rellena la columna
}

La segunda línea es la importante para la base: JPA solo mira al propietario. La primera mantiene la lista coherente mientras el objeto está en memoria. Así no se te olvida ninguno de los dos.

Paso 12 · Crear una relación uno a muchos

¿Uso List o Set para las colecciones?

List admite repetidos y guarda el orden; Set no admite repetidos. En un @ManyToMany conviene Set: si añades dos veces el mismo autor a un libro, el Set descarta el segundo y no se intenta insertar la misma fila dos veces en la tabla intermedia.

En los @OneToMany (médicos de un hospital, consultas de un paciente) un List va bien, porque cada hijo solo puede estar una vez en la base. Inicializa siempre la colección (= new ArrayList<>()): si no, vale null y add falla.

Paso 27 · Las trampas de comprensión

Repositorios y consultas 5 preguntasParte 1 · Data JPA

¿Qué me da JpaRepository sin escribir nada?

Al escribir public interface IMedicoRepository extends JpaRepository<Medico, Long> ya tienes, sin declararlos: save, findById, findAll, deleteById, delete, existsById y count. Spring escribe el código por ti.

Lo que va entre < > es qué entidad maneja (Medico) y de qué tipo es su id (Long). Un error típico es copiar un repositorio y dejar la entidad de otro.

No declares otra vez esos métodos: solo añades al repositorio las búsquedas nuevas (findByEspecialidad, countByMedicoId…).

Paso 7 · Crear la interfaz del repositorio

¿Cómo funcionan las consultas derivadas como findByEspecialidad?

Spring lee el nombre del método y escribe la consulta por ti. Se construye con piezas:

MétodoSe lee
findByEspecialidad(Especialidad e)Médicos con esa especialidad.
findByHospitalIdAndActivoTrue(Long id)Del hospital con ese id y activos.
findBySalarioGreaterThanOrderBySalarioDesc(BigDecimal s)Salario mayor que s, de mayor a menor.
countByMedicoId(Long id)Cuántas hay de ese médico.
existsByEmail(String email)¿Existe alguna con ese email? (true/false)

Los nombres tienen que ser los de los campos Java, con mayúscula inicial: findByNombre necesita un campo nombre. Si escribes mal uno, la aplicación no arranca y dice que no encuentra esa propiedad.

Paso 10 · Escribir consultas en la interfaz

¿Por qué funciona findByHospitalId si Medico no tiene un campo hospitalId?

Porque Spring sabe navegar por las relaciones. HospitalId se lee como «el campo hospital y, dentro de él, su id», es decir, medico.hospital.id. Como ese id es justo la columna id_hospital, la consulta ni siquiera necesita unir tablas.

Funciona igual con otros campos: findByHospitalNombre(String nombre) buscaría por el nombre del hospital.

Paso 10 · Escribir consultas en la interfaz

¿Cuándo hace falta @Query? ¿Qué diferencia hay entre JPQL y SQL?

Cuando el nombre del método no basta: agrupar con GROUP BY, sumar, unir varias tablas con condiciones raras… Entonces escribes tú la consulta encima del método con @Query.

  • JPQL usa los nombres de Java: la clase Medico y el campo hospital.
  • SQL (con nativeQuery = true) usa los de MySQL: la tabla medicos y la columna id_hospital.
@Query("SELECT h.nombre, COUNT(m) FROM Medico m JOIN m.hospital h GROUP BY h.id, h.nombre")
List<Object[]> contarPorHospital();

Los parámetros se escriben con dos puntos (:medicoId) y se enlazan con @Param("medicoId") en el argumento. Si una consulta derivada sirve, úsala: es más corta y más difícil de equivocarse.

Paso 15 · Escribir consultas en el repositorio

¿Qué es el Optional que devuelve findById?

Es una cajita que puede venir con el objeto dentro o vacía. findById lo devuelve porque el id que buscas puede no existir, y así te obliga a pensar en ese caso en vez de recibir un null por sorpresa.

Optional<Medico> medicoOpt = medicoRepository.findById(id);
if (medicoOpt.isEmpty()) {
    return null;                     // no existe
}
Medico medico = medicoOpt.get();     // existe: se saca de la caja

isEmpty() pregunta si está vacía, isPresent() si tiene algo y get() saca el objeto (solo si hay algo dentro; si está vacía, falla). En pruebas rápidas de run se usa a veces orElseThrow(), que saca el objeto o lanza un error si no está.

Paso 26 · Los controladores y los códigos de estado

DTO 6 preguntasParte 3 · API REST

¿Qué es un DTO y qué tipos hay (Request, Response y Resumen)?

DTO significa Data Transfer Object: un objeto simple, sin anotaciones de JPA ni lógica, que solo transporta datos entre el cliente y tu API. La entidad es cómo guardas los datos; el DTO es lo que enseñas y lo que pides por la red.

TipoPara quéEjemplo
RequestDTOLo que el cliente envía (POST, PUT). Sin id y con las relaciones como ids. Lleva las validaciones.MedicoRequestDTO(nombre, salario, especialidad, hospitalId)
ResponseDTOLo que la API devuelve. Con id y los datos ya preparados (el nombre del hospital, no el objeto).MedicoResponseDTO(id, nombre, especialidad, nombreHospital)
ResumenDTOUna versión reducida que va dentro de otra respuesta. Corta los bucles.ConsultaResumenDTO dentro de PacienteResponseDTO

Para decidir sus campos, pregúntate: ¿qué necesita el cliente en esta operación?

Paso 24 · ¿Qué es un DTO?

¿Por qué no devuelvo directamente las entidades en el controlador?

Por dos motivos:

  1. Bucle infinito. En una relación bidireccional, el hospital tiene sus médicos y cada médico apunta a su hospital. Al convertirlo a JSON, Jackson entra en hospital → médicos → hospital → médicos… y falla.
  2. Se expone la base de datos. El cliente vería campos internos, y cualquier cambio en una entidad cambiaría la API sin querer. Además, las relaciones LAZY se intentarían leer fuera de la transacción.

La regla de la guía: el controlador nunca importa una entidad. Solo DTO y la interfaz del servicio.

Paso 27 · Las trampas de comprensión

¿Por qué el RequestDTO lleva hospitalId y no el objeto Hospital?

Porque el cliente solo conoce los ids de lo que ya existe; no maneja objetos de la base. Además, así el cliente no puede cambiar los datos del hospital al crear un médico. Es el servicio quien busca el hospital real con hospitalRepository.findById(dto.hospitalId()) y lo asocia.

En la recepción dices «quiero pedir cita en el hospital número 1», no te llevas el hospital a cuestas.

Paso 24 · Los DTO como contrato de la API

¿Por qué los DTO se escriben como record?

Un record es una clase de Java pensada justo para transportar datos. En una línea declaras los campos, y Java crea solo el constructor, los métodos para leerlos y equals/toString:

public record MedicoResponseDTO(Long id, String nombre, Especialidad especialidad, String nombreHospital) {
}

Ojo con cómo se leen los campos: sin get. Es dto.nombre(), no dto.getNombre(). Y no tienen setters: un record no se modifica después de crearlo.

Paso 24 · Los DTO como contrato de la API

¿Dónde se convierte el DTO en entidad y la entidad en DTO?

Siempre en el servicio, que es la única capa que conoce las dos cosas:

  • DTO → entidad al crear: new Medico(dto.nombre(), dto.salario(), dto.especialidad(), true).
  • Entidad → DTO al devolver, en un método privado como mapearADTO(Medico m).

El controlador solo ve DTO y el repositorio solo ve entidades. Además, convertir dentro del servicio (que lleva @Transactional) permite leer las relaciones LAZY sin errores.

Paso 25 · Los servicios

¿Qué hace @Valid y qué validaciones pongo en el RequestDTO?

Las anotaciones van en los campos del RequestDTO y @Valid las activa en el controlador, delante de @RequestBody. Si el JSON no las cumple, Spring responde 400 sin llegar a ejecutar tu método.

AnotaciónQué exige
@NotNullQue venga (no null). Para números, fechas, enums, ids.
@NotBlankTexto que venga y no esté vacío ni sea solo espacios.
@EmailFormato de correo.
@PastFecha en el pasado.
@Pattern(regexp = "AL-\\d{4}")Que el texto siga un patrón.
@PositiveOrZero, @Min, @MaxLímites numéricos.

Pon solo las que pida el enunciado. Necesitan la dependencia Validation; los imports son de jakarta.validation.constraints.

Es el portero de la discoteca: si tu entrada no es válida, ni siquiera entras. El servicio solo atiende a quien ya pasó el control.

Paso 28 · Validación declarativa con @Valid

Servicio 8 preguntasParte 3 · API REST

¿Para qué sirve la capa de servicio? ¿No puede el controlador usar el repositorio?

Cada capa tiene un trabajo, y separarlas hace el código más fácil de entender y de cambiar:

  • Controlador: recibe la petición HTTP y elige el código de respuesta.
  • Servicio: la lógica (comprobar que el hospital existe, que el médico no tiene consultas…), las conversiones DTO ⇄ entidad y las transacciones.
  • Repositorio: hablar con la base.
Es un restaurante: el camarero (controlador) toma el pedido, la cocina (servicio) lo prepara y la nevera (repositorio) guarda los ingredientes. El camarero no entra en la nevera.

Paso 18 · Qué cambia al pasar a REST

¿Por qué el servicio tiene una interfaz y una implementación?

La interfaz (IMedicoService) es el contrato: la lista de cosas que el servicio sabe hacer. La implementación (MedicoService, con implements IMedicoService) es cómo las hace.

El controlador pide la interfaz (@Autowired private IMedicoService medicoService;) y Spring le da la implementación. Así el controlador no depende de los detalles: podrías cambiar la implementación sin tocarlo. En la implementación, cada método lleva @Override encima, para indicar que cumple uno del contrato.

Paso 25 · Cómo se escribe un método de la interfaz

¿Por qué el método eliminar es void?

void significa que el método no devuelve nada. Al borrar no hay ningún dato que enseñar: el recurso ya no existe, y la respuesta correcta es 204 No Content, que va sin cuerpo.

Los errores se resuelven antes de llamar a eliminar: el controlador comprueba si existe (si no, 404) y si se puede borrar (si no, 409). Cuando llega a eliminar ya sabe que va a salir bien, así que no necesita ninguna respuesta.

if (medicoService.obtener(id) == null) {
    return ResponseEntity.notFound().build();                    // 404
}
if (medicoService.tieneConsultas(id)) {
    return ResponseEntity.status(HttpStatus.CONFLICT).build();   // 409
}
medicoService.eliminar(id);
return ResponseEntity.noContent().build();                       // 204

La solución de la biblioteca de la guía usa otra forma válida: un int que cuenta qué pasó (1, 0 o -1).

Paso 25 · ¿Por qué eliminar puede ser void?

¿Qué hacen @Transactional y readOnly = true?

Una transacción es un grupo de operaciones que se hacen todas o ninguna. Con @Transactional sobre un método del servicio, Spring:

  1. Abre la transacción al entrar y la cierra al salir.
  2. Si todo va bien, guarda los cambios; si se lanza una excepción, los deshace todos.
  3. Mantiene la conexión con la base abierta durante el método, para poder recorrer relaciones LAZY sin LazyInitializationException.

readOnly = true avisa de que el método solo lee: Hibernate no vigila cambios para guardarlos, va algo más rápido y queda claro que no modifica nada.

MétodoAnotación
crear, actualizar@Transactional
obtener, listar…@Transactional(readOnly = true)
Uno que solo llama a un método del repositorio (deleteById, countBy…)Puede no llevarla: el repositorio ya trae la suya
Importa la de Spring, org.springframework.transaction.annotation.Transactional. La de jakarta.transaction no tiene readOnly.
Es una compra en el súper: o pagas todo el carro y te lo llevas, o no pagas nada. Nunca sales con media compra.

Paso 25 · @Transactional y readOnly

¿Por qué un servicio usa repositorios de otras entidades y no sus servicios?

Porque necesita la entidad de verdad para crear la relación, y los servicios solo devuelven DTO. Para crear un médico hay que asociarle el objeto Hospital, no un HospitalResponseDTO: con un DTO no se puede rellenar un @ManyToOne. Por eso MedicoService inyecta IHospitalRepository.

El cocinero necesita el tomate de verdad, no una foto del tomate. Va a la nevera (el repositorio), no al camarero.

Paso 25 · Los servicios

¿Qué hace cada método de la implementación del servicio (MedicoService)?
  • crear: busca el hospital con findById; si no existe, devuelve null. Si existe, crea el Medico con los datos del DTO, lo añade con addMedico, lo guarda con save y devuelve su DTO. Lleva @Transactional.
  • obtener: busca el médico; si no está, null; si está, lo convierte a DTO. Lleva readOnly porque, al convertir, lee el hospital (LAZY).
  • listarPorHospital: si el hospital no existe, null (para que sea un 404 y no una lista vacía). Si existe, recorre sus médicos, convierte cada uno y devuelve la lista.
  • tieneConsultas: devuelve true si countByMedicoId es mayor que cero.
  • eliminar: deleteById(id), nada más.
  • mapearADTO: privado. Fabrica el MedicoResponseDTO con id, nombre, especialidad y el nombre del hospital. Es lo que impide que la entidad salga del servicio.

Paso 25 · El «idioma» entre el servicio y el controlador

Controlador y HTTP 5 preguntasParte 3 · API REST

¿Qué hace cada parte del controlador?
  • @RestController: la clase atiende peticiones HTTP y lo que devuelven sus métodos se convierte en JSON.
  • @RequestMapping("/api/medicos"): el principio de la dirección de todos sus métodos.
  • @Autowired IMedicoService: pide la interfaz del servicio; Spring le da la implementación.
  • @PostMapping, @GetMapping, @PutMapping, @DeleteMapping: qué método HTTP atiende cada función, con el resto de la dirección entre paréntesis ("/{id}").
  • ResponseEntity<...>: la respuesta completa (código, cabeceras y cuerpo). Lo que va entre < > es el tipo del cuerpo.

El controlador no busca en la base ni convierte entidades: pregunta al servicio y elige el código. Por eso «no tiene lógica de negocio».

¿Qué diferencia hay entre @PathVariable, @RequestParam y @RequestBody?

¿Qué es la cabecera Location y cómo se construye?

En un 201 Created, Location dice dónde está el recurso nuevo: si creas el médico 7, vale http://localhost:8080/api/medicos/7. Así el cliente sabe qué dirección pedir después.

URI location = ServletUriComponentsBuilder.fromCurrentRequest()   // la dirección de esta petición: /api/medicos
        .path("/{id}")                                            // le añade /{id}
        .buildAndExpand(creado.id())                              // cambia {id} por el id del médico creado
        .toUri();
return ResponseEntity.created(location).body(creado);

Paso 26 · Los controladores y los códigos de estado

Al borrar un hospital con médicos sale un 500. ¿Por qué debería ser 409?

El 500 viene de MySQL: los médicos siguen apuntando al hospital y la clave foránea no deja borrarlo (DataIntegrityViolationException). Un 500 significa «el servidor ha fallado», y no es verdad: el problema es que la petición choca con los datos que hay. Eso es un 409 Conflict.

La solución es comprobarlo antes de borrar: el servicio ofrece una pregunta como tieneMedicos(id) (con un countByHospitalId), y si es true, el controlador responde 409 sin intentar el borrado.

Paso 27 · Las trampas de comprensión

Errores frecuentes 6 preguntasToda la guía

Me sale LazyInitializationException. ¿Qué pasa?

Estás usando una relación LAZY (por ejemplo medico.getHospital().getNombre()) cuando la conexión con la base ya se ha cerrado. El sustituto (proxy) no puede ir a buscar los datos.

Suele pasar cuando el servicio devuelve la entidad y es el controlador quien intenta recorrerla. Se arregla así:

  • Convierte a DTO dentro del servicio.
  • Pon @Transactional (o @Transactional(readOnly = true) si solo lee) en ese método, para que la sesión siga abierta mientras recorres las relaciones.

En la Parte 1, si te pasa dentro de run, anota run con @Transactional.

Paso 27 · Las trampas de comprensión

El JSON entra en un bucle infinito (o sale StackOverflowError). ¿Por qué?

Porque estás devolviendo una entidad con una relación bidireccional. Al convertirla a JSON, Jackson recorre hospital → médicos → hospital → médicos… sin fin, hasta que falla (Document nesting depth exceeds 500 o StackOverflowError).

La solución buena es devolver DTO: el MedicoResponseDTO lleva solo nombreHospital, no el hospital entero, y los *ResumenDTO no vuelven a apuntar al objeto que los contiene. También existen @JsonIgnore o @JsonManagedReference/@JsonBackReference, pero atan la entidad al formato JSON y no son lo recomendado.

Paso 27 · Las trampas de comprensión

Al listar salen muchísimas consultas en la terminal. ¿Qué es el problema N+1?

Una consulta trae la lista (por ejemplo, 50 pacientes) y después, al recorrer una relación LAZY de cada uno, Hibernate lanza otra consulta por cada elemento: 1 + 50. Funciona, pero es lento.

Se arregla en el repositorio, trayendo la relación en la misma consulta:

@Query("SELECT DISTINCT p FROM Paciente p LEFT JOIN FETCH p.consultas")
List<Paciente> listarConConsultas();

@EntityGraph(attributePaths = {"consultas"})
List<Paciente> findAll();

Lo ves con spring.jpa.show-sql=true: cuenta los select que salen.

Paso 27 · Las trampas de comprensión

Al arrancar dice No property … found for type. ¿Qué he hecho mal?

Una consulta derivada del repositorio usa un nombre que no es un campo Java de la entidad. findByNombre necesita un campo nombre; findByFechaNacimiento, un campo fechaNacimiento. Suele pasar al escribir el nombre de la columna SQL (fecha_nacimiento) o con una errata.

Compara letra a letra el nombre del método con el del campo, y recuerda que tras findBy va con mayúscula inicial.

Paso 16 · Corregir errores y terminar el proyecto

Postman me devuelve 415 Unsupported Media Type. ¿Por qué?

Porque el cuerpo no va marcado como JSON. En Postman, en la pestaña Body, hay que elegir raw y, en el desplegable de la derecha, JSON. Así Postman añade la cabecera Content-Type: application/json. Si lo dejas en Text, el servidor no sabe leerlo y responde 415.

Paso 19 · El puente paso a paso

¿Cómo sé qué escribir en el JSON?

Cada clave del JSON es un campo del RequestDTO, con el mismo nombre. Y cada tipo se escribe de una forma:

Tipo en el recordEn el JSON
StringEntre comillas: "Dra. Sara Gil"
Long, BigDecimal, intNúmero sin comillas: 1, 3900.00
Un enumEl nombre exacto de la constante, entre comillas: "PEDIATRIA"
LocalDate / LocalDateTimeTexto: "2002-07-21" / "2026-10-01T09:30:00"
Una lista (Set<Long>)Entre corchetes: [1, 2]
Otro record dentroUn objeto entre llaves: "ficha": { ... }

No se envía el id (lo pone MySQL) y las relaciones van como ids ("hospitalId": 1), que tienen que existir ya.

Paso 29 · Probar con Postman o curl

¿Cómo pruebo que mis errores 400, 404 y 409 funcionan?
  • 400: rompe el cuerpo. Envía {}, deja el nombre vacío ("") o pon una especialidad que no existe.
  • 404: apunta a un id que no existe: GET /api/medicos/99999, o un POST con "hospitalId": 99999.
  • 409: provoca el conflicto: borra un médico que tenga consultas (DELETE /api/medicos/1 con los datos del data.sql).

Comprueba el código de cada respuesta, no solo que «no da error»: un 200 donde esperabas un 404 también es un fallo.

3 y 6. Medico es el propietario de la relación con Hospital: tiene la clave foránea id_hospital, obligatoria y con carga perezosa. Su lista de consultas es el lado inverso y sin cascada.

package com.hospital.examen.entity;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

import com.hospital.examen.enums.Especialidad;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;

import jakarta.persistence.OneToMany;

@Entity
@Table(name = "medicos")
public class Medico {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_medico")
    private Long id;

    @Column(nullable = false)
    private String nombre;

    @Column(nullable = false, precision = 10, scale = 2)
    private BigDecimal salario;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private Especialidad especialidad;

    private boolean activo;

    // Lado propietario: aquí está la columna id_hospital
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "id_hospital", nullable = false)
    private Hospital hospital;

    // Lado inverso del N:M con datos, sin cascada
    @OneToMany(mappedBy = "medico")
    private List<Consulta> consultas = new ArrayList<>();

    public Medico() {}

    public Medico(String nombre, BigDecimal salario, Especialidad especialidad, boolean activo) {
        this.nombre = nombre;
        this.salario = salario;
        this.especialidad = especialidad;
        this.activo = activo;
    }

    public Long getId() { return id; }
    public String getNombre() { return nombre; }
    public BigDecimal getSalario() { return salario; }
    public Especialidad getEspecialidad() { return especialidad; }
    public boolean isActivo() { return activo; }
    public Hospital getHospital() { return hospital; }
    public void setHospital(Hospital hospital) { this.hospital = hospital; }
    public List<Consulta> getConsultas() { return consultas; }
}
  • ¿Quién es el propietario y por qué? Medico, porque es el que lleva @JoinColumn: su tabla guarda la columna id_hospital. En la base la relación es una sola columna, así que solo uno de los dos lados puede mandar sobre ella. Hospital es el lado inverso: su mappedBy = "hospital" dice «la relación ya está descrita en el campo hospital de Medico», y JPA no lo mira al guardar.
  • ¿Por qué el @ManyToOne va en Medico? Porque cada médico trabaja en un hospital, y eso cabe en una columna de su fila (id_hospital = 1). Al revés no cabría: un hospital tiene muchos médicos y no se pueden guardar varios ids en una sola columna. Se lee desde la clase: «muchos médicos → un hospital».
  • ¿Qué hace fetch = FetchType.LAZY? Al leer un médico no trae su hospital: deja un sustituto y solo lanza la consulta si de verdad usas el hospital (medico.getHospital().getNombre()). Sin escribirlo, el @ManyToOne sería EAGER y traería el hospital siempre.
  • ¿Lleva siempre @JoinColumn? No es obligatorio, pero sin él JPA llamaría a la columna hospital_id_hospital, que no es la que pide el enunciado ni la del data.sql. Con @JoinColumn(name = "id_hospital", nullable = false) eliges el nombre y la haces obligatoria.

Todo esto está explicado con más calma en el paso 12 de la guía.

4, 7 y 8. Paciente. Es el propietario del 1:1 con HistorialClinico (id_historial, obligatoria y única), con cascada total. Y es el lado «uno» de Consulta, con orphanRemoval. El constructor recibe el historial, así que es imposible crear un paciente sin él.

package com.hospital.examen.entity;

import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.OneToMany;
import jakarta.persistence.OneToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "pacientes")
public class Paciente {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_paciente")
    private Long id;

    @Column(nullable = false)
    private String nombre;

    @Column(name = "fecha_nacimiento", nullable = false)
    private LocalDate fechaNacimiento;

    // Propietario del 1:1. La cascada guarda y borra el historial junto con el paciente.
    @OneToOne(cascade = CascadeType.ALL, optional = false)
    @JoinColumn(name = "id_historial", nullable = false, unique = true)
    private HistorialClinico historial;

    // Lado inverso del N:M con datos: las consultas se borran con el paciente
    @OneToMany(mappedBy = "paciente", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Consulta> consultas = new ArrayList<>();

    // Lo necesita JPA para crear objetos al leer de la base. No lo uses tú.
    public Paciente() {}

    // Única forma de crear un paciente: obliga a darle su historial
    public Paciente(String nombre, LocalDate fechaNacimiento, HistorialClinico historial) {
        this.nombre = nombre;
        this.fechaNacimiento = fechaNacimiento;
        this.historial = historial;
    }

    public void addConsulta(Consulta consulta) {
        consultas.add(consulta);
        consulta.setPaciente(this);
    }

    public Long getId() { return id; }
    public String getNombre() { return nombre; }
    public LocalDate getFechaNacimiento() { return fechaNacimiento; }
    public HistorialClinico getHistorial() { return historial; }
    public List<Consulta> getConsultas() { return consultas; }
}

¿Qué es orphanRemoval y en qué se diferencia de cascade? cascade = CascadeType.ALL repite en las consultas lo que le hagas al paciente: si guardas el paciente, se guardan sus consultas nuevas; si lo borras, se borran. orphanRemoval = true va un paso más allá: si quitas una consulta de la lista (paciente.getConsultas().remove(c)), esa consulta se queda huérfana y se borra de la base. Es decir, cascade mira lo que le pasa al padre; orphanRemoval mira si el hijo sale de la lista. Aquí tienen sentido los dos porque una consulta no existe sin su paciente. En Medico no ponemos ninguno: borrar un médico no debe llevarse el historial de consultas de los pacientes. Lo tienes con una tabla comparativa en el paso 12 de la guía.

7 (pregunta). optional = false es una regla del modelo Java: dice que la relación es obligatoria, así que JPA no permite guardar un paciente sin historial (y puede optimizar sabiendo que nunca es nulo). unique = true (en el @JoinColumn) es una regla de la base de datos: crea una restricción de unicidad en id_historial, de modo que dos pacientes no pueden compartir el mismo historial. Sin ella la relación sería en realidad de uno a muchos. Junto con nullable = false (la columna no admite NULL), dejan la relación como «uno a uno obligatoria» tanto en Java como en MySQL.

8. Consulta es la entidad que representa la relación N:M con datos. Tiene dos @ManyToOne y es la propietaria de las dos claves foráneas.

package com.hospital.examen.entity;

import java.math.BigDecimal;
import java.time.LocalDateTime;

import com.hospital.examen.enums.TipoConsulta;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

@Entity
@Table(name = "consultas")
public class Consulta {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_consulta")
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "id_medico", nullable = false)
    private Medico medico;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "id_paciente", nullable = false)
    private Paciente paciente;

    @Column(nullable = false)
    private LocalDateTime fecha;

    @Column(nullable = false, precision = 10, scale = 2)
    private BigDecimal coste;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private TipoConsulta tipo;

    private boolean seguimiento;

    public Consulta() {}

    // Recibe los dos extremos: una consulta sin médico o sin paciente no tiene sentido
    public Consulta(Medico medico, Paciente paciente, LocalDateTime fecha, BigDecimal coste,
            TipoConsulta tipo, boolean seguimiento) {
        this.medico = medico;
        this.paciente = paciente;
        this.fecha = fecha;
        this.coste = coste;
        this.tipo = tipo;
        this.seguimiento = seguimiento;
    }

    public Long getId() { return id; }
    public Medico getMedico() { return medico; }
    public Paciente getPaciente() { return paciente; }
    public void setPaciente(Paciente paciente) { this.paciente = paciente; }
    public LocalDateTime getFecha() { return fecha; }
    public BigDecimal getCoste() { return coste; }
    public TipoConsulta getTipo() { return tipo; }
    public boolean isSeguimiento() { return seguimiento; }
}

¿Por qué el constructor de Consulta lleva el médico y el paciente? Porque una consulta no existe sin sus dos extremos: es «este médico atiende a este paciente, en esta fecha, por este coste». Sus dos @ManyToOne son obligatorios, así que las columnas id_medico e id_paciente no pueden quedar vacías. Si el constructor no los pidiera, podrías crear una consulta incompleta y el error solo saldría al guardar. Pidiéndolos, el compilador no te deja olvidarlos. Después, paciente.addConsulta(consulta) la añade también a la lista del paciente para que los dos lados queden sincronizados. Es lo mismo que hace Fichaje en el paso 13 de la guía.

9. Respuestas:

  • a) Porque la relación tiene datos propios (fecha, coste, tipo y seguimiento). Un @ManyToMany directo solo crea una tabla intermedia con dos ids y no puede guardar nada más. Con Consulta, la tabla intermedia pasa a ser una entidad con sus propias columnas, y la relación se convierte en dos @ManyToOne.
  • b) Las claves foráneas son medicos.id_hospital, pacientes.id_historial, consultas.id_medico y consultas.id_paciente. Siempre están en el lado propietario (el que lleva @JoinColumn); el lado con mappedBy no tiene columna.
  • c) Al borrar un hospital se borrarían también todos sus médicos (y, por la cadena de relaciones, podría fallar o arrastrar más datos), aunque tengan consultas históricas. Es una pérdida masiva de datos en vez de una protección de integridad. Por eso Hospital no lleva cascada, y borrar un hospital con médicos se responde con un 409.

package com.hospital.examen;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.time.LocalDateTime;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

import com.hospital.examen.entity.Consulta;
import com.hospital.examen.entity.HistorialClinico;
import com.hospital.examen.entity.Medico;
import com.hospital.examen.entity.Paciente;
import com.hospital.examen.enums.TipoConsulta;
import com.hospital.examen.repository.IMedicoRepository;
import com.hospital.examen.repository.IPacienteRepository;

@SpringBootApplication
public class HospitalApplication implements CommandLineRunner {

    @Autowired
    private IPacienteRepository pacienteRepository;

    @Autowired
    private IMedicoRepository medicoRepository;

    public static void main(String[] args) {
        SpringApplication.run(HospitalApplication.class, args);
    }

    @Override
    public void run(String... args) {
        // 1) El médico ya existe (lo cargó data.sql): solo hay que buscarlo
        Medico medico = medicoRepository.findById(2L).orElseThrow();

        // 2) El historial se crea primero porque el constructor de Paciente lo exige
        HistorialClinico historial = new HistorialClinico("H-0004", "0+", null);
        Paciente paciente = new Paciente("Lucas Prieto", LocalDate.of(2001, 6, 18), historial);

        // 3) La consulta se cuelga del paciente
        paciente.addConsulta(new Consulta(medico, paciente, LocalDateTime.now(), new BigDecimal("90.00"),
                TipoConsulta.PRESENCIAL, false));

        // 4) Un solo save: la cascada guarda el historial y la consulta
        pacienteRepository.save(paciente);
        System.out.println("Paciente guardado con id " + paciente.getId());
    }
}

Por qué este orden: el médico tiene que existir antes, porque la consulta apunta a él. El historial se crea antes que el paciente porque el constructor lo exige. Y gracias a cascade = ALL, un solo save(paciente) inserta el historial (primero, porque el paciente guarda su clave foránea), el paciente y, por último, la consulta, que necesita el id del paciente.

16. Dos motivos para no devolver las entidades:

  • Recursión infinita. Hospital tiene una lista de Medico y cada Medico apunta a su Hospital: al serializar a JSON, Jackson entra en un bucle (hospital → médicos → hospital → …) y falla con un StackOverflowError o similar. Los DTO, con sus «resúmenes», cortan el bucle.
  • Se expone la base de datos. La entidad lleva campos que el cliente no debe ver o decidir (ids internos, la lista completa de consultas, etc.), y atar la API a la entidad hace que cualquier cambio en el modelo rompa a los clientes. Además, las relaciones LAZY se intentarían leer fuera de la transacción (LazyInitializationException).

Y la implementación. Cada método que lee relaciones perezosas va con @Transactional, y la conversión a DTO se hace dentro del servicio:

package com.hospital.examen.service;

import java.util.ArrayList;
import java.util.List;
import java.util.Optional;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import com.hospital.examen.dto.MedicoRequestDTO;
import com.hospital.examen.dto.MedicoResponseDTO;
import com.hospital.examen.entity.Hospital;
import com.hospital.examen.entity.Medico;
import com.hospital.examen.repository.IConsultaRepository;
import com.hospital.examen.repository.IHospitalRepository;
import com.hospital.examen.repository.IMedicoRepository;

@Service
public class MedicoService implements IMedicoService {

    @Autowired
    private IMedicoRepository medicoRepository;

    @Autowired
    private IHospitalRepository hospitalRepository;

    @Autowired
    private IConsultaRepository consultaRepository;

    @Override
    @Transactional
    public MedicoResponseDTO crear(MedicoRequestDTO dto) {
        Optional<Hospital> hospitalOpt = hospitalRepository.findById(dto.hospitalId());
        if (hospitalOpt.isEmpty()) {
            return null;   // el hospital no existe
        }
        // DTO -> Entity. Un médico nuevo empieza activo.
        Medico medico = new Medico(dto.nombre(), dto.salario(), dto.especialidad(), true);
        hospitalOpt.get().addMedico(medico);
        return mapearADTO(medicoRepository.save(medico));
    }

    @Override
    @Transactional(readOnly = true)
    public MedicoResponseDTO obtener(Long id) {
        Optional<Medico> medicoOpt = medicoRepository.findById(id);
        if (medicoOpt.isEmpty()) {
            return null;   // el médico no existe
        }
        return mapearADTO(medicoOpt.get());
    }

    @Override
    @Transactional(readOnly = true)
    public List<MedicoResponseDTO> listarPorHospital(Long hospitalId) {
        if (!hospitalRepository.existsById(hospitalId)) {
            return null;   // el hospital no existe
        }
        List<MedicoResponseDTO> lista = new ArrayList<>();
        for (Medico m : medicoRepository.findByHospitalId(hospitalId)) {
            lista.add(mapearADTO(m));
        }
        return lista;   // una lista vacía es válida
    }

    @Override
    public boolean tieneConsultas(Long id) {
        return consultaRepository.countByMedicoId(id) > 0;
    }

    @Override
    public void eliminar(Long id) {
        medicoRepository.deleteById(id);
    }

    // Entity -> DTO (el hospital es LAZY: por eso se hace dentro de la transacción)
    private MedicoResponseDTO mapearADTO(Medico m) {
        return new MedicoResponseDTO(m.getId(), m.getNombre(), m.getEspecialidad(), m.getHospital().getNombre());
    }
}

Cómo comunica cada resultado: un hospital o un médico que no existen devuelven null, que el controlador convierte en 404. Un médico con consultas no se puede borrar: el controlador lo pregunta antes con tieneConsultas y responde 409. Una lista vacía no es un error: se devuelve vacía y es un 200.

La interfaz, método a método

Cada línea de IMedicoService se escribe pensando en tres cosas: qué devuelve al controlador, cómo se llama la acción y qué necesita recibir. Por ejemplo, MedicoResponseDTO crear(MedicoRequestDTO dto); se lee «crear recibe los datos que manda el cliente (el RequestDTO) y devuelve el médico creado, con su id (el ResponseDTO)». obtener solo necesita el id; listarPorHospital devuelve una List porque puede haber varios; tieneConsultas es una pregunta de sí o no, así que devuelve boolean. La explicación completa de cómo se escribe una firma está en el paso 25 de la guía.

¿Por qué eliminar es void?

void significa que el método no devuelve nada. Al borrar un médico no hay ningún dato que enseñar al cliente: la respuesta correcta es 204 No Content, que va sin cuerpo. Los dos casos de error ya se han resuelto antes de llamar a eliminar: el controlador comprueba con obtener si el médico existe (si no, 404) y con tieneConsultas si se puede borrar (si no, 409). Cuando llega a eliminar, ya sabe que el borrado va a salir bien, así que no necesita ninguna respuesta del servicio.

La implementación, método a método

  • @Service y los @Autowired. @Service le dice a Spring que cree un objeto de esta clase y lo tenga disponible para quien lo pida (el controlador). Los tres @Autowired son los repositorios que necesita: médicos para guardar y buscar, hospitales para comprobar que el hospital existe, y consultas para contar las de un médico. El servicio habla con los repositorios; el controlador no.
  • crear. Busca el hospital por el hospitalId que viene en el DTO. findById devuelve un Optional: una cajita que puede venir con el hospital dentro o vacía. Si está vacía (isEmpty()), el hospital no existe y devuelve null. Si existe, crea el Medico a partir de los datos del DTO (DTO → Entity), lo añade al hospital con addMedico (que rellena los dos lados de la relación), lo guarda con save y convierte lo guardado en MedicoResponseDTO (Entity → DTO). Lleva @Transactional porque escribe en la base.
  • obtener. Busca el médico por id. Si no está, null; si está, lo convierte a DTO. Lleva @Transactional(readOnly = true): solo lee, pero al convertir llama a m.getHospital().getNombre(), y el hospital es LAZY, así que la sesión tiene que seguir abierta.
  • listarPorHospital. Primero comprueba con existsById que el hospital existe; si no, null (para que el controlador responda 404 y no una lista vacía, que significaría «el hospital existe pero no tiene médicos»). Después recorre los médicos de ese hospital con un for, convierte cada uno a DTO y lo añade a una lista nueva. También es readOnly.
  • tieneConsultas. Cuenta las consultas del médico con countByMedicoId y devuelve true si hay más de cero. No lleva @Transactional: solo hace una llamada al repositorio, que ya trae su propia transacción, y no recorre relaciones.
  • eliminar. Una sola línea: deleteById(id) borra la fila del médico. Tampoco necesita @Transactional, por el mismo motivo.
  • mapearADTO. Es private porque solo lo usa este servicio. Recibe un Medico (entidad) y fabrica un MedicoResponseDTO con lo que el cliente necesita: id, nombre, especialidad y el nombre del hospital (no el objeto Hospital entero). Así es como la entidad nunca sale del servicio.
Sobre @Transactional y readOnly: @Transactional agrupa todo lo que hace el método en una transacción (o se guarda todo o nada) y mantiene abierta la conexión con la base mientras dura, para poder recorrer relaciones LAZY. readOnly = true avisa de que el método solo lee: va algo más rápido y deja claro que no cambia nada. Lo tienes explicado con calma en el paso 25 de la guía.

18. El controlador. Solo conoce el IMedicoService y los DTO. No tiene lógica de negocio: mira lo que devuelve el servicio y elige el código HTTP.

@RestController
@RequestMapping("/api/medicos")
public class MedicoController {

    @Autowired
    private IMedicoService medicoService;

    // POST /api/medicos -> 201 + Location | 400 (@Valid) | 404 (el hospital no existe)
    @PostMapping
    public ResponseEntity<MedicoResponseDTO> crear(@Valid @RequestBody MedicoRequestDTO dto) {
        MedicoResponseDTO creado = medicoService.crear(dto);
        if (creado == null) {
            return ResponseEntity.notFound().build();   // 404
        }
        URI location = ServletUriComponentsBuilder.fromCurrentRequest()
                .path("/{id}").buildAndExpand(creado.id()).toUri();
        return ResponseEntity.created(location).body(creado);
    }

    // GET /api/medicos/{id} -> 200 | 404
    @GetMapping("/{id}")
    public ResponseEntity<MedicoResponseDTO> obtener(@PathVariable Long id) {
        MedicoResponseDTO medico = medicoService.obtener(id);
        if (medico == null) {
            return ResponseEntity.notFound().build();   // 404
        }
        return ResponseEntity.ok(medico);
    }

    // GET /api/medicos?hospitalId=1 -> 200 (lista, puede estar vacía) | 404 (el hospital no existe) | 400 (falta hospitalId)
    @GetMapping
    public ResponseEntity<List<MedicoResponseDTO>> listarPorHospital(@RequestParam Long hospitalId) {
        List<MedicoResponseDTO> lista = medicoService.listarPorHospital(hospitalId);
        if (lista == null) {
            return ResponseEntity.notFound().build();   // 404
        }
        return ResponseEntity.ok(lista);
    }

    // DELETE /api/medicos/{id} -> 204 | 404 | 409 (tiene consultas)
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> eliminar(@PathVariable Long id) {
        if (medicoService.obtener(id) == null) {
            return ResponseEntity.notFound().build();                    // 404
        }
        if (medicoService.tieneConsultas(id)) {
            return ResponseEntity.status(HttpStatus.CONFLICT).build();   // 409
        }
        medicoService.eliminar(id);
        return ResponseEntity.noContent().build();                       // 204
    }
}

El controlador, pieza a pieza

  • @RestController indica que esta clase atiende peticiones HTTP y que lo que devuelven sus métodos se convierte en JSON. @RequestMapping("/api/medicos") es el principio de la dirección de todos sus métodos. @Autowired IMedicoService: el controlador pide la interfaz del servicio, no la clase; Spring le da la implementación.
  • ResponseEntity<...> es la respuesta HTTP completa: el código (200, 404…), las cabeceras y el cuerpo. Lo que va entre < > es el tipo del cuerpo. Se fabrica con métodos cortos: ResponseEntity.ok(x) es un 200 con x en el cuerpo; notFound().build(), un 404 sin cuerpo; noContent().build(), un 204 sin cuerpo; status(HttpStatus.CONFLICT).build(), un 409; created(location).body(x), un 201 con la cabecera Location.
  • crear (@PostMapping). @RequestBody convierte el JSON del cuerpo en un MedicoRequestDTO, y @Valid comprueba sus anotaciones (@NotBlank, @NotNull): si alguna falla, Spring responde 400 sin entrar en el método. Si el servicio devuelve null, el hospital no existe: 404. Si no, construye la dirección del médico nuevo (/api/medicos/7) con ServletUriComponentsBuilder y responde 201 con esa dirección en Location y el médico en el cuerpo.
  • obtener (@GetMapping("/{id}")). @PathVariable saca el 7 de /api/medicos/7 y lo mete en id. Si el servicio devuelve null, 404; si no, 200 con el médico.
  • listarPorHospital (@GetMapping). @RequestParam saca el valor de ?hospitalId=1. Es obligatorio: si falta, Spring responde 400. null significa que el hospital no existe (404); una lista, aunque esté vacía, es un 200.
  • eliminar (@DeleteMapping("/{id}")). Hace las comprobaciones en orden: primero si existe (si obtener da null, 404), después si tiene consultas (409), y solo entonces borra y responde 204. El orden importa: no tiene sentido decir «tiene consultas» de un médico que no existe.
El controlador no busca en la base ni convierte entidades: solo pregunta al servicio y elige el código. Por eso decimos que no tiene lógica de negocio.

package com.hospital.examen.service;

import java.util.ArrayList;
import java.util.List;
import java.util.Optional;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import com.hospital.examen.dto.ConsultaRequestDTO;
import com.hospital.examen.dto.ConsultaResumenDTO;
import com.hospital.examen.dto.PacienteResponseDTO;
import com.hospital.examen.entity.Consulta;
import com.hospital.examen.entity.Medico;
import com.hospital.examen.entity.Paciente;
import com.hospital.examen.repository.IConsultaRepository;
import com.hospital.examen.repository.IMedicoRepository;
import com.hospital.examen.repository.IPacienteRepository;

@Service
public class PacienteService implements IPacienteService {

    @Autowired
    private IPacienteRepository pacienteRepository;

    @Autowired
    private IMedicoRepository medicoRepository;

    @Autowired
    private IConsultaRepository consultaRepository;

    @Override
    @Transactional(readOnly = true)
    public PacienteResponseDTO obtener(Long id) {
        Optional<Paciente> pacienteOpt = pacienteRepository.findById(id);
        if (pacienteOpt.isEmpty()) {
            return null;   // el paciente no existe
        }
        return mapearADTO(pacienteOpt.get());
    }

    @Override
    @Transactional
    public ConsultaResumenDTO registrarConsulta(Long pacienteId, ConsultaRequestDTO dto) {
        // Las dos entidades a las que apunta la consulta
        Optional<Paciente> pacienteOpt = pacienteRepository.findById(pacienteId);
        Optional<Medico> medicoOpt = medicoRepository.findById(dto.medicoId());
        if (pacienteOpt.isEmpty() || medicoOpt.isEmpty()) {
            return null;   // falta alguna de las dos
        }

        Consulta consulta = new Consulta(medicoOpt.get(), pacienteOpt.get(), dto.fecha(), dto.coste(), dto.tipo(), false);
        pacienteOpt.get().addConsulta(consulta);
        return mapearConsulta(consultaRepository.save(consulta));
    }

    private ConsultaResumenDTO mapearConsulta(Consulta c) {
        return new ConsultaResumenDTO(c.getFecha(), c.getMedico().getNombre(), c.getTipo(), c.getCoste());
    }

    // Entity -> DTO (recorre las consultas, que son LAZY: por eso se hace dentro de la transacción)
    private PacienteResponseDTO mapearADTO(Paciente p) {
        List<ConsultaResumenDTO> consultas = new ArrayList<>();
        for (Consulta c : p.getConsultas()) {
            consultas.add(mapearConsulta(c));
        }
        return new PacienteResponseDTO(p.getId(), p.getNombre(), p.getHistorial().getNumeroHistorial(),
                p.getHistorial().getGrupoSanguineo(), consultas);
    }
}

Parte 5: preguntas de comprensión

20. LazyInitializationException. Ocurre al leer una relación LAZY (aquí, las consultas del paciente, o el médico de cada consulta) cuando la sesión de Hibernate ya se ha cerrado: por ejemplo, si el servicio devuelve la entidad y es el controlador quien intenta recorrerla. Se evita convirtiendo a DTO dentro del servicio y anotándolo con @Transactional (readOnly = true si solo lee), para que la sesión siga abierta mientras se recorren las relaciones.

21. El bucle infinito. La causa es que la relación es bidireccional: Hospital tiene la lista de médicos y cada Medico apunta a su Hospital. Al convertir a JSON, Jackson recorre hospital → médicos → hospital → médicos… sin fin. Dos soluciones:

  • Usar DTO en vez de entidades (la buena): el DTO de salida no tiene referencia de vuelta, o solo un resumen (nombreHospital).
  • Anotaciones de Jackson sobre las entidades: @JsonIgnore en el lado que no queremos serializar, o la pareja @JsonManagedReference / @JsonBackReference. Funciona, pero ata la entidad al formato JSON, por eso no es lo recomendable.

22. Borrar un hospital con médicos. El 500 viene de la base de datos (violación de clave foránea: los médicos siguen apuntando al hospital). Debería devolver 409 Conflict. Falta la comprobación previa, igual que con las consultas de un médico: el servicio la ofrece y el controlador responde 409 si hay médicos:

public boolean tieneMedicos(Long id) {
    return medicoRepository.countByHospitalId(id) > 0;
}

23. El esquema de tablas. Las claves foráneas (FK) están siempre en el lado propietario:

hospitales   (id_hospital PK, nombre, ciudad)
medicos      (id_medico PK, nombre, salario, especialidad, activo,
              id_hospital FK -> hospitales)                    1:N
historiales  (id_historial PK, numero_historial UNIQUE, grupo_sanguineo, alergias)
pacientes    (id_paciente PK, nombre, fecha_nacimiento,
              id_historial FK UNIQUE -> historiales)           1:1
consultas    (id_consulta PK, fecha, coste, tipo, seguimiento,
              id_medico   FK -> medicos,                       N:M con datos:
              id_paciente FK -> pacientes)                     dos 1:N hacia Consulta
Cómo corregirte. Parte 1 (3 puntos): enums, columnas y restricciones bien, la FK en Medico, mappedBy en Hospital, el constructor de Paciente con el historial y Consulta con sus dos @ManyToOne. Parte 4 (3 puntos): los DTO con sus validaciones, la conversión solo en el servicio, el controlador sin lógica de negocio y los códigos 201, 200, 204, 400, 404 y 409 bien elegidos. Si fallaste en lo de las relaciones, repasa los pasos 11 a 13; si fue en la API, los pasos 18 y 19.

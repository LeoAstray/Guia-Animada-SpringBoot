12 Crear una relación uno a muchos

Una relación uno a muchos significa que un objeto puede tener varios del otro tipo. En este ejercicio un equipo puede tener varios estadios, pero cada estadio pertenece a un solo equipo.

Primero veremos la relación en una dirección y después la convertiremos en dos direcciones. Son dos versiones de la misma relación; al final conservaremos la bidireccional.

Crear Estadio

1. Clic derecho en entity → New Java File → Class. Escribe Estadio y pega el archivo completo:

package leo.astray.examen.entity;

import jakarta.persistence.*;

@Entity
@Table(name = "estadios")
public class Estadio {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_estadio")
    private Long id;

    @Column(nullable = false, length = 100)
    private String nombre;
    @Column(nullable = false)
    private int capacidad;

    public Estadio() {}

    public Estadio(String nombre, int capacidad) {
        this.nombre = nombre;
        this.capacidad = capacidad;
    }

    public Long getId() { return id; }
    public String getNombre() { return nombre; }
    public int getCapacidad() { return capacidad; }
}

Crear Equipo con una lista de estadios

2. Crea Equipo.java de la misma manera y pega este código completo:

package leo.astray.examen.entity;

import jakarta.persistence.*;
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "equipos")
public class Equipo {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_equipo")
    private Long id;

    @Column(nullable = false, length = 100)
    private String nombre;
    @Column(nullable = false, length = 100)
    private String ciudad;
    @Column(nullable = false, precision = 14, scale = 2)
    private BigDecimal presupuesto;

    @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)
    @JoinColumn(name = "id_equipo")
    private List<Estadio> estadios = new ArrayList<>();

    public Equipo() {}

    public Equipo(String nombre, String ciudad,
            BigDecimal presupuesto) {
        this.nombre = nombre;
        this.ciudad = ciudad;
        this.presupuesto = presupuesto;
    }

    public Long getId() { return id; }
    public String getNombre() { return nombre; }
    public String getCiudad() { return ciudad; }
    public BigDecimal getPresupuesto() { return presupuesto; }
    public List<Estadio> getEstadios() { return estadios; }

    public void addEstadio(Estadio estadio) {
        estadios.add(estadio);
    }
}

List<Estadio> es la lista de estadios de ese equipo. Aquí necesitamos una colección porque puede haber varios. new ArrayList<>() prepara una lista vacía donde poder añadirlos; si no la creas, podrías tener null y no podrías usar add.

BigDecimal sirve para representar importes decimales exactos. Para dinero escribe, por ejemplo, new BigDecimal("100000.00"). precision = 14, scale = 2 permite 14 cifras en total, 2 de ellas decimales.

En esta primera versión puedes ir de Equipo a sus estadios, pero Estadio no tiene un campo para volver al equipo. Por eso se llama unidireccional. Aunque @JoinColumn esté escrito en Equipo, en este mapeo la columna id_equipo está en la tabla estadios.

Convertirla en bidireccional

3. Abre Estadio.java. Añade este atributo dentro de la clase, después de los otros campos, y los métodos junto a sus getters:

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "id_equipo", nullable = false)
private Equipo equipo;

public Equipo getEquipo() {
    return equipo;
}

public void setEquipo(Equipo equipo) {
    this.equipo = equipo;
}

Desde el punto de vista de un estadio, muchos estadios pueden apuntar al mismo equipo: por eso aquí escribimos @ManyToOne.

4. Vuelve a Equipo.java. Sustituye las dos anotaciones de la lista estadios por esta. Conserva una sola lista y elimina la antigua @JoinColumn de ese campo:

@OneToMany(mappedBy = "equipo", cascade = CascadeType.ALL,
    orphanRemoval = true)
private List<Estadio> estadios = new ArrayList<>();

5. En el mismo Equipo.java, sustituye el método addEstadio por este, que ahora rellena también el lado del estadio:

public void addEstadio(Estadio estadio) {
    estadios.add(estadio);
    estadio.setEquipo(this);
}

Ahora puedes ir de equipo a estadios y de estadio a equipo: es bidireccional. En la base sigue habiendo una sola columna estadios.id_equipo. mappedBy = "equipo" señala el campo Java equipo de Estadio; no se escribe id_equipo porque ese es el nombre SQL.

¿Quién es el propietario de la relación, y por qué uno sí y el otro no?

En la base de datos la relación es una sola columna: estadios.id_equipo. En Java, en cambio, la has escrito dos veces: la lista estadios de Equipo y el campo equipo de Estadio. Si las dos mandaran sobre la columna, JPA no sabría qué hacer cuando no coinciden. Por eso uno de los dos lados es el que manda: el propietario.

  • El propietario es el lado que lleva @JoinColumn. Al guardar, JPA mira su campo para rellenar la columna. Aquí es Estadio, con su campo equipo.
  • El lado inverso es el que lleva mappedBy. No tiene columna propia: mappedBy = "equipo" significa «esta relación ya está descrita en el campo equipo del otro lado». JPA lo usa para leer (rellenar la lista al consultar), pero no lo mira para escribir la clave foránea.

¿Por qué el propietario es Estadio y no Equipo? Porque el propietario tiene que ser el lado cuya tabla guarda la columna, y la columna solo cabe en la tabla de estadios (lo verás en la siguiente pregunta). En una relación uno a muchos el propietario es siempre el lado «muchos», el que lleva @ManyToOne. En el ejercicio del hospital es lo mismo: el propietario es Medico, que guarda id_hospital.

Piensa en un colegio. Cada alumno tiene en su ficha «soy de la clase 3B». La clase no guarda una lista fija en ningún sitio: para saber quién está en 3B, miras las fichas de los alumnos. Manda la ficha del alumno, no la clase.
Consecuencia práctica: si solo hicieras equipo.getEstadios().add(estadio) sin estadio.setEquipo(equipo), al guardar la columna id_equipo quedaría vacía (y aquí fallaría por nullable = false), porque JPA solo mira el lado propietario. Por eso addEstadio rellena los dos lados.

¿Por qué el @ManyToOne va en Estadio (y en Medico)?

Una columna de una fila solo puede guardar un valor. Un estadio es de un solo equipo, así que en su fila cabe sin problema id_equipo = 1. Al revés no se puede: un equipo tiene varios estadios, y no hay forma de meter «2, 5 y 7» en una sola columna de la fila del equipo. Por eso la clave foránea va en la tabla del lado «muchos», y el campo Java que la representa es el @ManyToOne.

equipos   (id_equipo PK, nombre, ciudad, presupuesto)
estadios  (id_estadio PK, nombre, capacidad, id_equipo FK)   <- la clave foránea vive aquí

El nombre se lee desde la clase en la que está escrito. En Estadio: «muchos estadios → un equipo», @ManyToOne. En Equipo: «un equipo → muchos estadios», @OneToMany. En el hospital: muchos médicos trabajan en un hospital, así que Medico lleva @ManyToOne private Hospital hospital; y Hospital lleva @OneToMany(mappedBy = "hospital") private List<Medico> medicos;.

¿Qué hace fetch = FetchType.LAZY?

Decide cuándo se carga el objeto relacionado. Con LAZY (perezoso), al leer un estadio JPA trae solo sus columnas y deja en equipo un «sustituto» (un proxy) que conoce el id del equipo pero todavía no tiene sus datos. La consulta del equipo solo se lanza si de verdad lo usas, por ejemplo al llamar a estadio.getEquipo().getNombre().

Con EAGER (ansioso) es al revés: trae el equipo siempre, lo uses o no. Si no escribes nada, @ManyToOne y @OneToOne son EAGER, y @OneToMany y @ManyToMany son LAZY. Por eso escribimos LAZY a mano en el @ManyToOne: si listas 100 estadios, no queremos 100 consultas extra para traer equipos que quizá ni miras.

Es como un regalo envuelto: sabes que está ahí, pero no lo abres (no se lanza la consulta) hasta que lo necesitas.
La pega: el sustituto solo se puede «abrir» mientras la conexión con la base sigue abierta. Si lo usas después, salta LazyInitializationException. Lo verás en la Parte 3 (paso 27), y se evita con @Transactional en el servicio (paso 25).

¿El @ManyToOne lleva siempre @JoinColumn?

No es obligatorio, pero conviene ponerlo siempre. Sin @JoinColumn, JPA se inventa el nombre de la columna juntando el nombre del campo y el de la clave primaria a la que apunta: aquí sería equipo_id_equipo. Funcionaría, pero ese nombre no coincide con el que pide el enunciado ni con el de tu data.sql, y los INSERT fallarían.

Con @JoinColumn(name = "id_equipo", nullable = false) eliges tú el nombre de la columna y, con nullable = false, impides que quede vacía. Lo que nunca lleva @JoinColumn es el lado inverso, el del mappedBy: ese lado no tiene columna.

¿Qué es orphanRemoval y en qué se diferencia de cascade?

cascade = CascadeType.ALL significa: lo que le hagas al padre, házselo también a sus hijos. Si guardas el equipo, se guardan sus estadios nuevos; si borras el equipo, se borran sus estadios.

orphanRemoval = true significa: el hijo que se queda sin padre se borra. Si quitas un estadio de la lista (equipo.getEstadios().remove(estadio)), ese estadio queda «huérfano» y JPA borra su fila al guardar los cambios. Sin orphanRemoval, quitarlo de la lista no borraría nada.

Lo que hacesSolo cascade = ALLSolo orphanRemoval = true
Guardar un equipo nuevo con estadios nuevosSe guardan también los estadiosLos estadios no se guardan solos: hay que guardarlos aparte
Borrar el equipoSe borran sus estadiosSe borran sus estadios (se quedan huérfanos)
Quitar un estadio de la listaNo se borra nadaSe borra ese estadio

En resumen: cascade se fija en lo que le pasa al padre; orphanRemoval se fija en lo que le pasa a la relación (si el hijo sale de la lista). Se ponen juntos cuando el hijo no tiene sentido sin su padre: un estadio sin equipo, una consulta sin paciente. No se ponen cuando el hijo vive por su cuenta: en el hospital, borrar un hospital no debe borrar a sus médicos, así que Hospital no lleva ninguno de los dos.

cascade: si tiras la caja de juguetes a la basura, los juguetes van dentro. orphanRemoval: si sacas un juguete de la caja, ese juguete se tira.

Probarlo

Un ejemplo de creación, para usar dentro de run si el ejercicio lo pide, sería:

Equipo equipo = new Equipo(
    "Estrellas", "Madrid", new BigDecimal("100000.00"));
Estadio estadio = new Estadio("Campo Norte", 5000);

equipo.addEstadio(estadio);
equipoRepository.save(equipo);

Este ejemplo explica la operación; no lo copies además de los datos iniciales del paso 14. Allí se crearán ya esos registros con SQL. Para usarlo necesitarías importar java.math.BigDecimal en la clase principal y tener el repositorio de equipos que crearemos en ese paso.

13 Representar una relación muchos a muchos

Una relación muchos a muchos permite que varios objetos de un tipo se relacionen con varios del otro. Un jugador puede pasar por distintos equipos a lo largo de su carrera y cada equipo puede tener muchos jugadores.

Hay dos formas según lo que pida el examen. Si solo necesitas unir jugador y equipo, sirve @ManyToMany. Si además debes guardar precio, temporada o tipo de operación, crea Fichaje.

El proyecto que seguimos construyendo usa Fichaje. La primera opción es una explicación alternativa; no la añadas al modelo final.

Opción A: cuando solo interesa la unión

La base necesita una tabla intermedia con un ID de jugador y un ID de equipo. En Jugador el mapeo podría ser:

@ManyToMany
@JoinTable(name = "jugadores_equipos",
    joinColumns = @JoinColumn(name = "id_jugador"),
    inverseJoinColumns = @JoinColumn(name = "id_equipo"))
private Set<Equipo> equipos = new HashSet<>();

public Set<Equipo> getEquipos() {
    return equipos;
}

public void addEquipo(Equipo equipo) {
    equipos.add(equipo);
    equipo.getJugadores().add(this);
}

En Equipo, el otro lado sería:

@ManyToMany(mappedBy = "equipos")
private Set<Jugador> jugadores = new HashSet<>();

public Set<Jugador> getJugadores() {
    return jugadores;
}

Ambos archivos necesitarían import java.util.Set; e import java.util.HashSet;. Un Set es una colección que evita elementos repetidos según la igualdad de los objetos Java. Aquí lo usamos para representar una pertenencia sin repetir el mismo objeto.

@JoinTable da nombre a la tabla intermedia. joinColumns corresponde al propietario, aquí el jugador; inverseJoinColumns, al equipo. mappedBy = "equipos" apunta al atributo de Jugador.

No pongas cascada de borrado hacia los equipos: borrar un jugador no debe borrar los equipos compartidos con otros jugadores.

Opción B: crear Fichaje con sus propios datos

1. Para seguir el tutorial, conserva Jugador, Equipo, Estadio y PerfilEstadistico de los pasos anteriores. Si habías copiado la opción A, quita sus campos equipos y jugadores, las anotaciones y los métodos que dependen de ellos. No mantengas las dos formas para el mismo historial.

2. Clic derecho en enums → New Java File → Enum. Crea PeriodoMercado y pega:

package leo.astray.examen.enums;

public enum PeriodoMercado {
    VERANO,
    INVIERNO
}

3. Crea del mismo modo TipoOperacion:

package leo.astray.examen.enums;

public enum TipoOperacion {
    TRASPASO,
    CESION,
    LIBRE
}
Un enum es una lista cerrada de valores permitidos. Es como elegir entre los sabores escritos en un menú: puedes usar VERANO o INVIERNO, pero no inventarte un texto distinto por error.

Los archivos también terminan en .java; la palabra enum indica qué estás creando.

4. Clic derecho en entity → New Java File → Class. Crea Fichaje y pega este archivo:

package leo.astray.examen.entity;

import jakarta.persistence.*;
import java.math.BigDecimal;
import leo.astray.examen.enums.PeriodoMercado;
import leo.astray.examen.enums.TipoOperacion;

@Entity
@Table(name = "fichajes")
public class Fichaje {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id_fichaje")
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "id_jugador", nullable = false)
    private Jugador jugador;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "id_equipo", nullable = false)
    private Equipo equipo;

    @Column(nullable = false, length = 5)
    private String temporada;
    @Column(nullable = false, precision = 14, scale = 2)
    private BigDecimal precio;
    @Column(name = "clausula_pagada", nullable = false)
    private boolean clausulaPagada;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 10)
    private PeriodoMercado mercado;
    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 10)
    private TipoOperacion tipo;

    public Fichaje() {}

    public Fichaje(Jugador jugador, Equipo equipo,
            String temporada, BigDecimal precio,
            boolean clausulaPagada, PeriodoMercado mercado,
            TipoOperacion tipo) {
        this.jugador = jugador;
        this.equipo = equipo;
        this.temporada = temporada;
        this.precio = precio;
        this.clausulaPagada = clausulaPagada;
        this.mercado = mercado;
        this.tipo = tipo;
    }

    public Long getId() { return id; }
    public Jugador getJugador() { return jugador; }
    public Equipo getEquipo() { return equipo; }
    public String getTemporada() { return temporada; }
    public BigDecimal getPrecio() { return precio; }
    public boolean isClausulaPagada() { return clausulaPagada; }
    public PeriodoMercado getMercado() { return mercado; }
    public TipoOperacion getTipo() { return tipo; }

    public void setJugador(Jugador jugador) {
        this.jugador = jugador;
    }
}
Un fichaje es como un recibo que dice «este jugador ha fichado por este equipo, en esta temporada y por este precio».

Por eso tiene dos relaciones muchos a uno: muchos fichajes pueden apuntar al mismo jugador y muchos al mismo equipo.

¿Por qué el constructor de Fichaje recibe al jugador y al equipo?

Porque un fichaje no existe sin sus dos extremos. Sus dos @ManyToOne son obligatorios (optional = false y nullable = false): en la tabla fichajes, las columnas id_jugador e id_equipo no pueden quedar vacías. Si el constructor no los pidiera, podrías crear un new Fichaje(...) sin jugador o sin equipo, y el error solo aparecería al guardar, como un fallo de la base de datos.

Al pedirlos en el constructor pasa lo mismo que con el perfil del jugador en el paso 11: el compilador no te deja crear un fichaje incompleto, y el error sale en rojo en VS Code, antes de ejecutar. Además se lee como una frase: new Fichaje(jugador, equipo, "26/27", precio, ...) es «este jugador ficha por este equipo, en esta temporada, por este precio».

Fíjate en que los otros datos (temporada, precio, mercado, tipo) también van en el constructor, pero el id no: lo pone MySQL al guardar. Y el constructor vacío sigue existiendo solo porque JPA lo necesita al leer filas.

En el ejercicio del hospital pasa lo mismo con Consulta: una consulta es «este médico atiende a este paciente, en esta fecha, por este coste». Por eso su constructor recibe Medico medico, Paciente paciente antes que el resto de datos. Después, paciente.addConsulta(consulta) la añade también a la lista del paciente, para que los dos lados queden sincronizados en memoria.
@Enumerated(EnumType.STRING) guarda el nombre del valor, por ejemplo VERANO. El SQL debe usar ese mismo texto. No escribas verano o CESIÓN si tus constantes son VERANO y CESION.

5. Abre Jugador.java. Añade los imports java.util.List y java.util.ArrayList debajo de los demás imports. Dentro de la clase añade este campo, su getter y el método de ayuda:

@OneToMany(mappedBy = "jugador", cascade = CascadeType.ALL,
    orphanRemoval = true)
private List<Fichaje> fichajes = new ArrayList<>();

public List<Fichaje> getFichajes() {
    return fichajes;
}

public void addFichaje(Fichaje fichaje) {
    fichajes.add(fichaje);
    fichaje.setJugador(this);
}

6. Abre Equipo.java. Añade este campo y su getter dentro de la clase. Ya tienes los imports de List y ArrayList:

@OneToMany(mappedBy = "equipo")
private List<Fichaje> fichajes = new ArrayList<>();

public List<Fichaje> getFichajes() {
    return fichajes;
}
No vuelvas a generar los constructores. Conserva los que ya tienen Jugador (el vacío y el de 4 parámetros del paso 11: nombre, mote, posición y perfil), Equipo y el resto. Las listas fichajes no van en ningún constructor: nacen vacías y se llenan después con addFichaje. Si usas Generate Constructors y marcas fichajes, cambias la forma de crear un jugador y el código de los pasos 11 y 19 deja de compilar. Si solo necesitas getters y setters que falten, genera únicamente esos.

Los dos campos mappedBy señalan los atributos de Fichaje, que es quien guarda las claves foráneas. No añadas otra @JoinColumn en esas listas. En Equipo no ponemos cascada de borrado para los fichajes: si un equipo tiene historial asociado, primero hay que decidir qué pide el ejercicio que hagamos con ese historial.

Para crear un fichaje desde Java, el equipo debe existir o guardarse antes. El constructor de Fichaje recibe al jugador y al equipo; después puedes usar jugador.addFichaje(fichaje) y guardar el jugador para propagar el guardado al fichaje. Si estás usando también la lista inversa de ese equipo en memoria, añade el fichaje a equipo.getFichajes() para mantenerla sincronizada.
